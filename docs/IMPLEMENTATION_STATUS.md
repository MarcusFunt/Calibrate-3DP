## Implemented foundation

- Python >=3.11 headless core, existing profile import/inheritance resolution, provenance and unknown-key preservation, deterministic ironing plans, manual result contracts, and separate Orca jobs.
- Database schema v4 contains persistent printer, material, grouped calibration-run, frozen experiment-configuration, assessment-revision, decision, and export records while preserving existing session rows and payloads. The v3-to-v4 migration retains schema-v1 config payloads and accepts schema v2 for new backend/recipe snapshots. Versioned profile snapshots retain raw documents, resolved values, provenance, and source fingerprints. Plan/sample data stays in SQLite; logs, 3MF, and G-code stay in per-run artifact folders with hashes and checked paths.
- The Qt configuration review uses the same connected layout builder as generation, shows the nine A–I mappings and geometry preview without allocating a plate code, freezes the configuration before generation, and links each run to that configuration revision and profile hashes.
- `AssessmentService` stores versioned per-run manual assessment revisions with optimistic concurrency. Optional local photos are copied into the run evidence area and checked by extension, signature, size, containment, and hash. Qt Experiment Details edits all nine candidate outcomes, ratings, defect tags, notes, photos, winner/ties, and a separately recorded physical-trial attestation.
- `RunDecisionService` stores recommendations tied to an exact assessment revision and creates immutable child configurations for refinement or confirmation. A confirmed acceptance stores the exact linked child assessment revision ID; decision schema v2 still reads schema-v1 records. Synthetic and incomplete physical attestations remain exploratory and cannot unlock acceptance. `RunExportService` reviews only a supported `ironing_flow`/`ironing_speed` patch, preserves the source profile's other keys, rechecks source hashes and evidence, and stores export hashes/history after writing a new process JSON, manifest, and report.
- Profile discovery/import and saved-record workflows connect to Qt. Users can add a printer from installed or local JSON/ZIP profiles, add nozzle-contextual filament records, reopen a printer workspace, start a nine-sample ironing run asynchronously, cancel it, inspect run history, and look up a run by its six-character code. Orca executable and profile roots are configurable in Settings.
- The first-party Orca-specific 3MF writer keeps per-sample object/part settings IDs. Schema-v1 packages contain nine samples plus the legacy frame; new schema-v2 CAD packages contain nine samples, a separate frame, and a separate plaque. The grouped-run service saves each STL and geometry manifest and checks shared placement against the selected bed and keep-outs. The CLI uses `--arrange 0 --orient 0`.
- The `stdlib-voxel` geometry adapter (0.4 mm grid) creates nine separately addressable watertight specimens, eight 2.4 × 0.8 mm breakaway links per sample, raised bitmap A–I labels, and a raised six-character code on the shared rail frame. It checks resolved machine bed polygons and explicit keep-outs, validates mesh closure/object mappings, and produces deterministic meshes. Binary STL and connected-mesh 3MF package tests pass locally.
- New schema-v2 ironing configurations default to pinned `build123d@1` with `ironing.flat_coupon@2`: each sample is one CAD solid with pocketed, bed-facing embossed text; the connected grid frame and raised-top corner identifier are distinct objects; and the plaque has two declared tabs. Geometry, recipe/font/native-library identities, and tolerances are recorded. Missing CAD/font inputs fail closed. Schema-v1 configuration decoding and its `stdlib-voxel@1` interpretation remain intact.
- The Qt printer workspace reopens saved initial configuration drafts after repository restart. Experiment Details reports geometry status, printed-mark presence, sample-settings and sliced-layout status, G-code preflight findings, Orca identity/support qualification, assessment state, artifacts, and remaining blockers; it opens an artifact only after repository path and hash verification. It has no printer-control action; successful sample-settings/layout validation is still `print_ready: false`.
- The Qt shell now has a global header for saved printer/material context, six-character plate lookup, and Settings, plus a compact horizontal route bar. Printer Workspace groups existing controls into Overview, Experiments, and Printer and materials tabs; Experiment Details uses Inspect, Assess, Decision, and Export tabs and explains the current export gate in the Export view. Workflow states combine plain labels, distinct drawn icons, and status tints; form and table borders have stronger contrast. Offscreen visual previews were checked after loading Segoe UI directly because this headless Qt font database exposed no families; manual high-DPI, screen-reader, and physical-monitor review remains open.
- A Qt-independent calibration package provides frozen dependency rules, contexts, evidence and state values; it validates rule IDs/references/cycles, evaluates required versus recommended rules deterministically, tracks accepted-result prerequisites and lifecycle precedence, and propagates relevant input changes. `CalibrationStateService` assembles the saved printer/material, nozzle, selected-profile, source-hash, run, assessment, and decision evidence for the existing ironing flow × speed calibration. New generation is blocked before allocating a plate code, run, or artifact directory when a required prerequisite fails.
- Generated ironing runs retain a versioned dependency snapshot with evaluated inputs, saved and current source hashes, parent references, and rule outcomes. Legacy runs remain readable; missing reconstructable evidence is shown as `needs_review` without rewriting the record. The Qt workspace renders the service status, blockers, recommendations, and `can_start` value. Its generation action is gated by that value, while a separate message keeps calibration state distinct from print readiness; `print_ready` remains false.
- The bounded G-code preflight tracks modal linear XYZE movement, printable-area/keep-out crossings, Z bounds, temperature limits and waits, unsupported commands, and unverified context. It treats zero temperature setpoints as heater shutdowns. It is not a complete Orca dialect or a hardware-safety certification.
- Generation records the source and derived profiles, exact Orca argument vector, CLI banner, G-code header, logs, bounds, and artifact hashes. The run is marked `settings_validated`; `print_ready` remains false.
