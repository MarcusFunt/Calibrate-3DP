# Experiment Configuration and Generation Proposal

**Status: adopted for the bounded grouped-ironing workflow through configuration review, manual assessment, follow-up, and reviewed-export paths (2026-10-10).** The broader architecture remains a proposal. Evidence supports versioned profile, plan, sample, configuration, assessment, decision, and export records in SQLite; hash-referenced per-run artifacts; a standard-library 3MF settings package; and a first-party standard-library voxel geometry backend for this bounded plate. This does not settle the complete experiment compiler contract, physical readability/handling acceptance, complete G-code validation, or supported layout/version matrix.

## Assessment

The core idea is strong: save a complete, versioned experiment description and generate geometry and slicer inputs from that description. This gives the project one auditable source for what a plate was meant to test, makes code lookup useful after printing, and lets the UI, compiler, and future import/export tools share the same data contract.

The main adjustment I recommend is to avoid treating “the configuration file”, database row, CAD model, Orca project, and G-code as one artifact. They have different roles and lifetimes. Use one typed configuration model, persist its canonical snapshot and the compiled sample map in the database, and treat geometry, Orca project, G-code, logs, and previews as immutable output artifacts linked by hash. A portable JSON representation can be exported/imported, but it should serialize the same schema rather than become a second source of truth.

This approach also avoids saving large mesh and G-code binaries inside SQLite. The database still contains the full structured plate definition, generated sample mapping, versions, profile snapshots/fingerprints, code, and artifact hashes/locations. The actual generated files can live in an app-managed artifact directory, with checksums and recovery checks in the database.

## Recommended separation of responsibilities

1. **Experiment configurator:** PySide6 views and forms gather module choice, factors, candidate ranges, fixed context, plate layout, sample labels, and applicable dependency overrides. It emits typed data; it does not generate CAD scripts or write Orca files itself.
2. **Experiment configuration:** A versioned, schema-validated value object captures the user's request: printer/material/profile snapshot IDs, calibration definition/version, chosen factors and options, layout strategy and dimensions, candidate count/order, deterministic seed, and explicit overrides.
3. **Compiler:** A headless service validates dependencies and capabilities, expands factors into concrete candidate samples, resolves held-constant settings, assigns sample mappings, and returns an immutable compiled experiment. The same compiler contract serves both the GUI and any future command-line or import/export path.
4. **Geometry backend:** A replaceable Python geometry adapter turns the compiled plate layout into connected grids, zones, towers, labels, and deliberate separation features. A “connected: on/off” toggle alone is too weak: connector shape, width, thickness, clearance, and separation mode affect handling and must be typed and validated.
5. **Orca adapter:** Separately packages/imports the geometry, associates samples with supported per-object or per-height setting changes, invokes Orca, then validates the actual G-code against the compiled sample map. Geometry generation must not imply that Orca applied the requested settings.
6. **Experiment history/inspect view:** A searchable Experiments workspace accepts a six-character plate code and displays the immutable configuration, compiled candidates, profiles, geometry and G-code artifacts, slicer validation, manual observations, and later refinement links. A revised configuration creates a new experiment/plate revision and code; it does not overwrite prior evidence.

The logical flow is:

`ExperimentConfig` → dependency/capability validation → `CompiledExperiment` → plate layout → Python geometry backend → Orca adapter and slice → output validation → immutable run/artifacts → manual assessment.

## Determinism and record identity

“Deterministic” should mean that the same normalized configuration, input profile snapshots, calibration-definition version, compiler version, geometry-backend version, and seed produce the same candidate order, sample labels, settings, and layout. Store those inputs and the compiled manifest. Retain the generated artifact and its SHA-256; future library versions must not be assumed to recreate byte-identical meshes or G-code.

The saved experiment configuration describes immutable inputs and does not contain a physical plate code. Preview never allocates a permanent code. When generation creates a physical run, allocate a unique six-character code, store it as indexed run identity, and include it in the generated geometry and manifest. A repeat run from the same configuration receives a new code; a linked refinement/confirmation configuration also receives its own run code. Enforce database uniqueness with collision retry. Do not derive the short code from a truncated hash without collision checking.

The canonical schema should be versioned. A migration can transform an older config into a newer in-memory representation, but old experiment snapshots and artifacts stay available in their original form. Reject unknown major schema versions with a useful message rather than silently discarding fields.

## Geometry backend decision (2026-10-09)

A small geometry adapter remains appropriate, but a general CAD runtime was not justified by the actual plate geometry. This pass uses axis-aligned specimen blocks, orthogonal rails, equal cross-section tabs, and raised bitmap glyphs. A deterministic first-party voxel union is sufficient for those features and exports triangle meshes without an additional runtime package.

- **build123d** was measured as the initial candidate: it is a Python parametric BREP framework over OpenCascade and documents STL and STEP export. Its project is Apache-2.0. Sources: [project](https://github.com/gumyr/build123d), [import/export documentation](https://build123d.readthedocs.io/en/stable/import_export.html), [license](https://github.com/gumyr/build123d/blob/dev/LICENSE). The isolated Windows environment measured 688.5 MiB in `Lib/site-packages`, so it was not added.
- **CadQuery** remains a possible later option if future geometry needs general BREP operations: Python parametric CAD over OCP/OpenCascade, with STL/STEP export and Apache-2.0 licensing. Its published dependency set is also broad. Sources: [project](https://github.com/CadQuery/cadquery), [import/export documentation](https://github.com/CadQuery/cadquery/blob/master/doc/importexport.rst), [setup.py](https://github.com/CadQuery/cadquery/blob/master/setup.py), [license](https://github.com/CadQuery/cadquery/blob/master/LICENSE).
- **lib3mf** may help package generated meshes into a standard 3MF file; it is not the CAD modeler and does not supply Orca-specific project settings. Its official project uses BSD-2-Clause. Sources: [project](https://github.com/3MFConsortium/lib3mf), [license](https://github.com/3MFConsortium/lib3mf/blob/master/LICENSE).

The isolated Windows Python 3.11 install/import probe for build123d 0.13.0 succeeded, but its `Lib/site-packages` occupied 721,973,890 bytes (about 688.5 MiB) and pulled 45 distributions, including a 47.5 MB OpenCascade wheel and large scientific/visualization packages. This exceeds the project's dependency and desktop packaging budget for the bounded geometry. Its upstream project is Apache-2.0: [build123d repository](https://github.com/gumyr/build123d), [import/export docs](https://build123d.readthedocs.io/en/stable/import_export.html), [PyPI release](https://pypi.org/project/build123d/0.13.0/).

CadQuery was not installed: its official packaging configuration declares OpenCascade plus additional DXF, scientific, native, and visualization dependencies (including VTK/trame-related packages), while the target geometry needs no BREP operations. The source is Apache-2.0: [CadQuery repository](https://github.com/CadQuery/cadquery), [upstream setup.py](https://github.com/CadQuery/cadquery/blob/master/setup.py), [import/export docs](https://github.com/CadQuery/cadquery/blob/master/doc/importexport.rst). This is a scope-based packaging decision, not a claim that CadQuery is unusable.

The chosen `stdlib-voxel` backend is versioned `1` and uses a 0.4 mm grid. It validates a 3 × 3 set of independent sample objects, eight object-to-frame links per sample (2.4 mm wide × 0.8 mm high with 2.8 mm clearance), a shared 2.4 mm rail frame, 0.8 mm raised A–I bitmap labels, and a six-character raised code on the front rail. Each sample and the frame exports as a closed, consistently oriented mesh. Binary STL and the streamed standard-library 3MF package are tested on the current Windows Python environment. A real Orca round-trip on the recorded Windows binary/profile confirms the nine settings-bearing object IDs remain distinct from the frame and reach their intended toolpaths; this is not a support-matrix entry. No build123d, CadQuery, or lib3mf runtime dependency was added.

The bitmap and mesh tests establish that label/code geometry exists and is manifold. The 2026-10-10 review of retained real Orca G-code now confirms that the A-I marks, six-character code, and connector regions produce front-face/connector toolpaths for the recorded run. This establishes what that slice depicts; it does not establish human readability on a physical print, tab durability, or hand-separation force. Keep the backend adapter replaceable if later geometry requires curved/boolean CAD operations or if measured packaging evidence changes.

The 2026-10-09 gate extended the original three-coupon Orca test to the connected 3 × 3 project and proved the per-sample settings, but the later review found the resulting G-code was auto-arranged: the settings result did not prove a connected plate. The 2026-10-10 correction disables automatic arrangement and orientation, and the integration gate now verifies that every named object's positive-extrusion XY bounds retain the mesh layout under one shared translation. On the tested local pair, the ten objects retain a common 0.2 mm shift, all nine samples pass flow/speed validation, and an omitted Sample-E override fails at the 5 mm/s baseline. The offscreen Qt workflow also saves, slices, validates, and looks up a connected nine-sample run. A follow-up identity probe found no Windows FileVersion/ProductVersion resource or advertised `--version` option. The CLI banner `OrcaSlicer-01.10.01.50` and G-code header `OrcaSlicer 2.3.0` are mapped by the official [v2.3.0 version.inc](https://github.com/SoftFever/OrcaSlicer/blob/v2.3.0/version.inc), which declares both the application release and slicer-engine version. This maps the labels but does not authenticate the local binary or qualify this executable/profile/platform for support; output remains not print-ready. Physical mark readability, physical link handling, other profile/platform combinations, and the full G-code contract remain open. Sources: [Orca import/export](https://www.orcaslicer.com/wiki/general_settings/import_export), [Orca CLI mode](https://www.orcaslicer.com/wiki/cli/cli_mode), and the retained test artifacts listed in `docs/PROGRESS_HISTORY.md`.

## Scoped geometry backend decision (2026-10-10)

The user-supplied build123d implementation plan resolves the backend only for new grouped-ironing geometry that needs pocketed underside embossing and a separate corner code plaque. New `ExperimentConfig` schema-v2 snapshots select `build123d@1`, `ironing.flat_coupon@2`, and layout version 2. Historical schema-v1 configurations continue to decode their original layout options and use `stdlib-voxel@1`; readers do not infer a new plaque from old code-on-rail metadata. SQLite config storage migration v4 explicitly accepts both frozen config payload versions without rewriting historical JSON.

The `[cad]` optional dependency extra pins `build123d==0.13.0` and `cadquery-ocp-novtk==8.0.1.1.0`. This keeps the measured 688.3 MiB CAD dependency footprint out of the default install while making the runtime reproducible when the user chooses that backend. CAD selection is explicit and fails closed if its optional runtime or pinned font is missing or changed; it never falls back to voxel output. The first-party Orca-specific 3MF writer remains the settings boundary and was tested with eleven named objects and nine per-sample overrides. The font asset and its SIL OFL 1.1 attribution are documented in `REUSE_RESEARCH.md` and distributed with the package.

This scoped choice does not settle the general experiment-config/compiler contract or the proposed overall schema/backend/storage split. Real Orca G-code has passed positive layout/settings/feature gates on one recorded Windows executable/profile set, with a negative missing-override case. The captured Orca logs also contain `Unable to create exclude triangles`. No physical trial or comprehensive G-code safety qualification has been performed; geometry does not set `print_ready`.

## Required architecture spike before committing to a backend

1. Measure install/import cost and licensing for a candidate general CAD library before adding it to the desktop runtime.
2. Use the first-party voxel backend for this axis-aligned specimen grid, equal breakaway links, raised A–I labels, and six-character code; keep the output behind a narrow adapter.
3. Validate bed bounds, distinct sample meshes/names, connector geometry, label placement, watertightness, and repeat-generation stability with deterministic tests.
4. Package/import the output in the exact Orca executable/profile under consideration. Assign different settings to all nine samples, slice, and prove each reaches its intended toolpath. Include an intentionally invalid missing/mismapped case that must be blocked.
5. Record commands, environment, input config, tool versions, hashes, Orca logs, G-code findings, platform packaging impact, and the decision in `docs/PROGRESS_HISTORY.md`.
6. Keep the full canonical experiment representation, human-readable physical marks/handling acceptance, additional connected layouts, and supported layout/settings matrix open. The narrow persistence split, voxel geometry, and standard-library 3MF package now have implementation evidence scoped to this local workflow.

## Recommendation

Proceed with the architecture concept as a design candidate: one typed/versioned experiment configuration, persisted and searchable through the database; a GUI configurator that creates that data; one headless deterministic compiler; a Python geometry backend; a separate Orca application/validation adapter; and a searchable experiment history view keyed by the plate code. The bounded grouped-ironing workflow now includes saved configuration review, manual assessment, linked follow-up, and export review. It does not yet demonstrate a physically eligible export or the complete generic compiler and history contracts.

The implementation adopts the separation of records from large artifacts, the grouped Orca 3MF mapping, and the bounded standard-library connected geometry backend. Physical mark readability/handling, portable configuration import/export, full experiment compilation, and the broad capability matrix remain open. This evaluation does not authorize camera workflows, automatic assessment, or any other excluded V1 feature.

## Persistence decision for immutable grouped-run workflow (2026-10-10)

Use an additive SQLite schema v3 migration with separate typed tables for saved experiment configurations, run-to-configuration links, assessment revisions, decisions, and exports. Each row has explicit identity/revision/link columns and a strict versioned JSON payload decoded through a typed domain record. Add foreign keys, uniqueness constraints, and lookup indexes for experiment revision and run history. Continue storing generated meshes, G-code, and copied photos outside SQLite with relative paths, byte sizes, and SHA-256 values. `SessionRepository` remains the sole schema migration owner; the v1 sessions and current v2 printer/material/run tables are preserved. Do not use a generic mutable event blob or append later assessment/export data to the immutable generation row.

Rationale: the current v2 code already separates durable identity and indexed lookup columns from typed JSON snapshots, and stores large artifacts separately. The distinct configuration, observation, decision, and export lifecycles require independent immutable revisions and database-enforced relationships. This is a scoped storage choice for the grouped ironing workflow; it does not settle a portable compiler configuration, a general calibration catalog, or an app-wide event system. The migration and record validators must reject unknown major versions and preserve historical rows. Cost if this schema proves insufficient: a later migration will be needed to normalize additional queryable fields or introduce an event model.

## Bounded workflow implementation record (2026-10-10)

The implemented Qt path freezes the resolved ironing plan, candidate map, profile snapshots/hashes, and connected layout before generation. Plate codes are allocated to generated runs, so configuration preview is repeatable and does not reserve physical identities. Assessment revisions, run decisions, linked refinement/confirmation configurations, and reviewed export records are stored separately and linked by IDs. The export writer is limited to a new process JSON plus manifest and report, and only patches the supported ironing flow/speed settings. Synthetic or incomplete physical evidence cannot unlock acceptance or export.

The bounded G-code preflight is integrated into run details, but the retained Orca output remains failed/incomplete: machine commands are unsupported, motion setup and bed-temperature limits are unverified, and one nozzle target falls below the saved material range. No physical coupon or plate was printed, so code/label readability and connector handling remain external acceptance gates. No physically eligible export was written. See `docs/IMPLEMENTATION_STATUS.md` and the dated `docs/PROGRESS_HISTORY.md` entry for commands, hashes, skips, and artifact locations.
